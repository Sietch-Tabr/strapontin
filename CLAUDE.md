# CLAUDE.md — strapontin (strapontin.kwaite.fr)

## Architecture — monorepo Maven

`java/{core,sources,web,worker}` (BOM parent `java/pom.xml`, Java 25, Spring Boot 4.1.0) — `core` : normalisation/dédup/types partagés ; `sources` : clients TM/Eventim/Digitick/Deezer ; `web` : REST API + Vue SPA (8080) ; `worker` : Quartz (8081). `scripts/` : provisionnement/déploiement/sauvegarde — noms auto-descriptifs sauf `restore-test.sh` (test de restauration à la demande, jamais en CI, voir section Sauvegarde).

## Architecture module web — couche service/repository

Pattern 3-couches : `XxxController` (HTTP) → `XxxService` (`@Transactional`) → `XxxRepository` (SQL pur, `NamedParameterJdbcTemplate`, package-private) — non-universel, une vingtaine de services anciens/simples n'ont pas de repository dédié, mais c'est la référence pour tout nouveau service non trivial. `GlobalExceptionHandler` : `NoResourceFoundException`→404, `HttpRequestMethodNotSupportedException`→405, `AuthenticationException`→401, `DuplicateKeyException`→409, `DataAccessException`→500.

**Services notables** : `SourceConcerts`/`SourceAvecFetchLot` (module `sources`) rend `WorkerService` source-agnostique — ajouter une source = une classe + un bean Spring, identifiants salle préfixés (`"tm:venueId"`). `WorkerService`/`AdminService`/`EmailService` sont scindés par responsabilité (`WorkerStatsService`/`WorkerFetchService`/`WorkerPurgeService`/`WorkerRevocationService` ; `ConfigAdminService`/`JobsAdminService` ; `EmailService`/`EmailAlerteService`/`EmailSender`). `core.BilanFetch`/`sources.SourceAvecBilanFetch` : bilan de panne agrégé partagé par toutes les sources (escalade `logs_admin error` sur panne totale), plutôt qu'un mécanisme par source.

**Enrichissement Wikidata/OSM/Deezer** (worker, package `enrichissement`) : `SourceEnrichissementSalle`/`SourceEnrichissementArtiste` (pattern extensible), orchestré par `EnrichissementSallesService`/`EnrichissementArtistesService`, lots de 25, rotation nocturne hebdomadaire `jour_batch` (`smallint` 1-7 = ISODOW) plutôt qu'un plafond fixe — index partiel `(jour_batch) WHERE wikidata_id IS NULL` sur `salles`/`artistes` (v2.8.7) calqué sur le filtre exact du cycle nocturne, pour éviter un scan complet de la table chaque nuit. `WikidataSalleSource.decouvrir` : 3 replis sur le nom (complet → tronqué au séparateur → sans dernier mot), toujours validés contre le nom complet (`estDoublonSalle`) — élargit les candidats, jamais le critère d'acceptation ; rejette un candidat si `salle.ville()` et la commune Wikidata (P131) sont incohérentes. `construireRequeteDecouverte` exige des coordonnées (`wdt:P625`) sauf exception vérifiée pour le type `wd:Q1060829` (bâtiment de salle de concert) — une salle réelle sans coordonnées ne doit pas être exclue au point qu'un homonyme sans rapport devienne l'unique candidat retourné ; `TYPES_EXCLUS` (public, réutilisé par la revalidation ci-dessous) exclut gare/tram/administratif/bar/restaurant. `CorrespondanceSalle.estDoublonSalle(a, b, pivotAutorise)` : le critère pivot (le plus faible des cinq) est désactivé en découverte quand le candidat n'a ni commune ni code postal Wikidata connus — un adjectif générique français (« nouvelle ») ne doit pas suffire seul sans signal de localisation pour un contrôle croisé. `CoherenceWikidataSalleService.revaliderTypes()` (cycle nocturne) revalide tous les `wikidata_id` déjà stockés contre `TYPES_EXCLUS` et les remet à `null` si désormais exclus — un garde-fou de type introduit après coup ne s'appliquait jusqu'ici qu'aux nouvelles découvertes. `WikidataArtisteSource` filtre P106 humain+musicien/humoriste ou groupe, bloque sur ambiguïté de type plutôt que deviner. `CoherenceWikidataSalleService` (`worker.sante`) : contrôle a posteriori `wikidata_id`/`concerts.ville` vs `salles.ville`, journalise sans changer le matching — `salles.coherence_wikidata_signalee` mémorise la signature de la dernière incohérence déjà journalisée pour ne pas re-signaler indéfiniment un état déjà connu. `ClientSparqlWikidata` retente les erreurs transitoires (502, content-type de réponse inattendu, comme le 503 déjà géré) ; `OverpassSalleSource` interrompt un cycle après 3 échecs consécutifs (circuit-breaker) plutôt que de brûler le reste du batch sur une instance publique manifestement indisponible — le compteur est un champ d'instance couvrant tout le cycle nocturne (pas seulement le lot de persistance courant, `EnrichissementSallesService.TAILLE_LOT_PERSISTANCE`), réarmé par `preleverBilan()` pour le cycle suivant. `SourceAvecBilanFetch.seuilAppelsMinAlerte()` (défaut : `BilanFetch.SEUIL_APPELS_MIN_ALERTE_DEFAUT`) est surchargeable par source — `OverpassSalleSource` le relève au-dessus de ce qu'un seul déclenchement du disjoncteur peut produire, pour qu'une coupure brève n'escalade pas systématiquement en alerte email "panne totale". `core.CorrespondanceSalle`/`core.CorrespondanceArtiste` : un seul algorithme de dédoublonnage flou par entité, partagé `sources`/`web`/`worker` (détail des seuils : [wiki Architecture](https://codeberg.org/Kwaite/strapontin/wiki/Architecture)). `ReconciliateurSalles` (v2.8.7) est désormais une façade de délégation pure (contrat public inchangé pour ses appelants) vers trois collaborateurs par responsabilité : `ReconciliationNomsSalles` (variantes de nommage intra-lot/inter-jobs, absorption des renommages), `ResolveurSalleParConcert` (résolution/création d'une salle pour un concert entrant — `chercherSalleParTokens`, `chercherSalleParCleForte`, `upsertSalleSource`) et `ReconciliateurSallesOrphelines` (retentative nocturne des concerts sans salle) — extraction pure de taille (626→~100 lignes de façade), aucun changement fonctionnel. `chercherSalleParCleForte` (v2.8.3, désormais `ResolveurSalleParConcert`) : dernier repli avant création d'une salle — quand un nom Eventim abrégé/stylisé ne partage aucun token avec le nom TM complet (ex. « Ed&n »/« Espace Dollfus Noack »), un concert déjà en base partageant exactement `artiste_norm`+`date`+`heure`+`dept` avec une autre source suffit à rattacher la salle indépendamment du nom. `FusionSallesClePorteeService` (v2.8.4, `worker.persister`, cycle nocturne) étend cette même clé forte à deux salles **déjà établies** chacune de leur côté (pas seulement à la résolution d'un concert entrant) : détecte les paires partageant un concert identique et les fusionne automatiquement (gabarit de fusion dupliqué de `ReferentielSallesService.fusionner`, web, non accessible depuis le worker), chaque fusion journalisée dans `logs_admin` (jamais silencieuse). `detecterPaires` (v2.8.5) filtre en plus les paires par `CorrespondanceSalle.estDoublonSalle` sur les noms — le seul critère artiste+date+heure+dept, sans comparaison de nom, s'est révélé insuffisant en production (concert coïncidant par erreur upstream, ex. mapping `salle_sources` corrompu, fusionnant à tort deux salles sans rapport réel).

**Santé/référentiel admin** : `ReconciliationNocturneService`+`SuiviSanteSourcesService` (`sante`, worker) : health-check IDs TM (3h), compteur passif réinitialisé par la vérification active. `ReferentielSallesService`/`ReferentielArtistesService` (web, `admin`) : onglets Salles/Artistes, fusion de doublons (dédoublonne aussi les `salle_sources`/`artiste_sources` en conflit par colonne `source` avant réassignation). Statut artiste `a_jour`/`invalide` piloté par `artiste_sources.necessite_intervention_le` (posé uniquement par `ReconciliationNocturneService`, effacé par un fetch positif cohérent ou une résolution manuelle) — le compteur passif seul générait 65% de faux positifs. La comparaison nom suivi/nom TM passe par `CorrespondanceArtiste.estDoublonArtiste` (même algorithme flou que la réconciliation) plutôt qu'une égalité stricte post-normalisation, pour ne jamais signaler un écart purement cosmétique (espace, article). Pour un écart réel jugé acceptable par un admin (nom de scène, ex. `-M-`/Matthieu Chédid), `ReferentielArtistesService.ignorerIntervention` mémorise le nom TM accepté dans `artiste_sources.nom_tm_ignore` (recopié depuis `nom_tm_incoherent`, rafraîchi à chaque détection) — la vérification nocturne ne resignale que si le nom TM change encore, jamais pour la même divergence déjà acceptée.

**Pagination admin** (v2.8.7) : `ReferentielSallesService`/`ReferentielArtistesService` (`page`/`totalPages`/`total`, `COUNT(*) OVER()` calculé dans la même exécution que la page plutôt qu'un `COUNT(*)` séparé, repli sur un second `COUNT` uniquement si la page demandée dépasse le total) — même pattern désormais étendu à `AdminService.listerUtilisateurs`, `ConcertsAdminService.lister` et `SourcesService.listerSalles` (endpoint dédié `GET /api/admin/sources/salles`, recherche par nom et bascule Digitick/sans-source côté serveur — `GET /api/admin/sources` ne renvoie plus que les statuts de sources).

**Sécurité admin/sessions** : `AdminService`/`SetupService`/`PushService`/`SalleService` isolent leurs opérations sensibles en transaction `SERIALIZABLE` (`REQUIRES_NEW`/`NESTED`) + retry, via auto-injection par setter (`@Autowired setSelf(@Lazy X self)`, pas par constructeur — évite l'auto-référence en test).
⚠️ **Ne jamais appeler une méthode `REQUIRES_NEW`+`SERIALIZABLE` depuis une transaction déjà ouverte** — épuisement garanti du pool HikariCP (incident réel). `AdminService.modifierUtilisateur` rejette donc la combinaison nom/email + rétrogradation admin en un seul `PATCH`.
`session_appareils` associe un `appareil_id` opaque à chaque session (jamais le `session_id` réel côté client). `AppareilEnregistrementInterceptor` (pas le contrôleur de login) enregistre l'appareil au premier appel API _suivant_ le login — Spring Session ne persiste la session qu'après la réponse du login lui-même. Les trois points de construction d'URL de base pour un lien envoyé par email (`AuthController`, `ParametresRestController`, `AdminController`) refusent tous l'envoi (503/blocage silencieux selon le flux) si `PUBLIC_BASE_URL` n'est pas configurée, plutôt que de se rabattre sur le header `Host` de la requête entrante (Host Header Injection). `users.two_factor_secret` chiffré (v2.8.7, `ConfigCipher`/`APP_CONFIG_SECRET`, même mécanisme qu'`app_config`) plutôt qu'en clair — lecture avec repli sur la valeur brute en cas d'échec de déchiffrement (comptes déjà enrôlés avant le chiffrement).

`VapidKeyGenerator` (`fr.strapontin.web`, v2.8.7) : génération de clé EC P-256 partagée entre `SetupService` (première génération) et `VapidService` (régénération admin) — dupliquée verbatim auparavant.

**`resoudreParUrl`/`EligibiliteResolutionDeezer`** (`worker.persister`) : `PersisteurConcertsDb.resoudreParUrl` est scopé à Eventim uniquement (pages festival) — appliqué à toutes les sources, il empêchait `supprimerDoublonsParUrl` (auto-guérison par URL) de jamais s'engager. `ReconciliateurArtistes.reconcilierUnArtiste` distingue, via `EligibiliteResolutionDeezer`, un concert éligible à la résolution Deezer (nom potentiellement corruptible — l'entrant converge vers l'existant, comportement protecteur conservé) d'un concert inéligible (nom brut fiable — corrige alors rétroactivement la ligne déjà en base via `UPDATE` SQL directe). `PersisteurConcertsDb.alignerHeureReportTM` (v2.8.5) aligne l'heure d'une ligne Ticketmaster déjà en base sur celle d'un report entrant (même url/date, nouveau statut `rescheduled`/`cancelled`/`postponed`) avant l'upsert — uniquement si une seule heure distincte existe déjà pour ce couple url/date : certaines productions à représentations multiples (théâtre, cirque) partagent un seul idmanif Ticketmaster pour plusieurs séances le même jour, l'ambiguïté laisse alors la ligne entrante s'insérer normalement plutôt que de risquer d'altérer la mauvaise représentation. `PersisterConcerts.resoudreIdentitesSources` (v2.8.5) valide aussi la cohérence géographique (département) d'un mapping `salle_sources` réutilisé avant de lui faire confiance — un identifiant source réattribué en amont (TM) à un lieu différent du mapping historique court-circuitait sinon tous les garde-fous appliqués à la création d'un nouveau mapping. `alignerHeureReportTM` (v2.8.6) filtre désormais `c.statut() != null` avant `STATUTS_REPORT_TM.contains(...)` — un `Set.of(...)` immuable lève une `NullPointerException` sur `.contains(null)` plutôt que de renvoyer `false`, faisant échouer toute la transaction du lot dès qu'un event TM de type « package » (`statut` toujours `null`) y figurait.

**Statut de vente cross-source** (v2.8.4) : `PersisteurConcertsDb.SQL_UPSERT_CONFLIT` protège désormais `statut` par `COALESCE(EXCLUDED.statut, concerts.statut)`, indépendamment de la colonne `source` — l'ancienne protection (`concerts.source='ticketmaster' AND EXCLUDED.source='eventim'`) ne survivait pas à deux cycles Eventim/Digitick consécutifs (`source` elle-même écrasée sans condition à chaque upsert). `Dedoublonner.scoreCompletude` compte désormais la présence d'un `statut` connu, pour que la fusion intra-lot (même cycle de fetch, TM+Eventim combinés) ne le perde pas non plus au profit d'une source qui ne le détermine jamais (Eventim/Digitick, toujours `null`). `MapeurEvenementTM` : un event `offsale` n'est requalifié `presale` que si la date de prévente connue (`sales.presales[0].startDateTime`) est encore dans le futur (sinon reste `offsale`, comme la branche `sales.public` déjà en place) ; les events de type « package » (VIP/bundle, détectés par le seul signal disponible — le motif d'URL `/pack/`, TM n'exposant aucun champ documenté distinct) ne portent plus de statut de vente notifiable, sans être exclus de la persistance.

**Bean Validation** : tout endpoint `@RequestBody` prend un DTO record annoté (`@NotBlank`/`@Size`/etc.) + `@Valid` — jamais de `Map<String,String>` brut. `@Valid` ne s'exerce que via le pipeline Spring MVC réel, jamais sur un appel Java direct : tester la validation via `Validator.validate(new Record(...))` (pattern `RequeteXxxValidationTest`). Exceptions documentées : `ForgotPasswordRequest` (anti-énumération), `ClientController` (bag ouvert borné autrement), `ResendWebhookController` (payload signé Svix).

**Onboarding** (`front/src/components/ModaleEtapes.vue`) : composant générique à étapes (dialog natif, Suivant/Précédent/Terminer), réutilisable pour un futur flux similaire (ex. annonce de mise à jour majeure) — piloté par `useOnboarding.js`/`OnboardingModal.vue` pour la modale de bienvenue actuelle. `verifierOnboarding()` doit être rappelée non seulement au montage de `App.vue` mais aussi dans son `watch(estPageAuth)` (sortie d'une page d'authentification) — l'activation d'un compte invité fait un `router.push` SPA, pas un rechargement complet, donc l'unique `onMounted` s'exécute avant la connexion et échoue en 401 sans ce second point d'entrée (même pattern déjà en place pour `chargerSession`/`chargerBanniere`).

**okhttp/Resend (Kotlin Multiplatform)** : l'artefact `com.squareup.okhttp3:okhttp` est vide côté JVM depuis okhttp 5.0.0 — exclusion + dépendance `okhttp-jvm` requise dans **les deux** `java/web/pom.xml` **et** `java/worker/pom.xml` (l'oubli côté worker a déjà causé un `NoClassDefFoundError` silencieux sur tout email worker).

## Stack technique (v2.2.0)

- **Spring Boot 4.1.0** + **Vue 3 + Vite 8.1** (`front/` → `static/`) — port 8080. Thymeleaf et HTMX supprimés.
- **Vitest 4** (`front/vitest.config.js`, v2.6.2, #781) : tests unitaires des fonctions pures partagées entre composants (`front/src/utils/`), sans montage de composant ni jsdom — complémentaire à Playwright (flux utilisateur, rendu réel), pas redondant. Config dédiée séparée de `vite.config.js` pour ne pas embarquer les plugins Vue/PWA dans l'exécution des tests.
- **Spring Security 7** — auth session, TOTP 2FA optionnel (bucket4j rate-limiting) ; `anyRequest().authenticated()` — non-API sans session → redirect `/login`, API → 401 JSON
- **Spring Data JDBC** + PostgreSQL 18 — données persistantes. `statement_timeout=30s` / `idle_in_transaction_session_timeout=30s` (protection contre une transaction bloquante qui épuiserait le pool HikariCP, cf. incident v2.6.3). Tuning mémoire (`shared_buffers`/`work_mem`/`effective_cache_size`) laissé aux valeurs par défaut PostgreSQL — base ~16 MB (juillet 2026), aucun gain mesurable à un tuning mémoire à ce volume.
- **Quartz** — jobs background (fetch concerts) ; `threadPool.threadCount=10` (virtual threads)
- **Flyway 13** — migrations DB (`java/web/src/main/resources/db/migration/`)
- **Resend** — notifications email (tier gratuit 3 000/mois) ; gabarits HTML via `EmailTemplates.java` (text blocks Java)
- **web-push (VAPID)** — notifications push PWA
- **Maven** — build (`mvn -f java/pom.xml -pl web,worker -am package`). Version CI-friendly (v2.6.1, #764) : `<revision>` dans `java/pom.xml` (parent), `${revision}` dans les 4 pom.xml enfants — un seul bump met à jour tout le monorepo.

### Gestion des issues (Codeberg) et Git

CLI : `tea` (pas `gh` — Codeberg est Gitea, incompatible avec `gh`). `tea issue view N` → toujours `-f "index,title,body"` (body absent par défaut). Labels : `Bug`, `Feature`, `Question`, `Task`, `Duplicate`, `Invalid`. PR : `Closes #N` **dans le corps** (`--description`), pas seulement le titre — Gitea ferme les issues via le corps, jamais via le titre.

`main` : Woodpecker déploie sur prod à chaque push (**jamais de push manuel sans build valide**). Features : branche `feature/xxx` → PR → merge. Pipeline (`.woodpecker/ci.yaml`) : test (Maven) + test-front (Vitest) → build-front → build → backup → deploy, restreints à `main`. Le repo doit être marqué "trusted" (Settings → repo) pour autoriser les volumes Maven.

## Sauvegarde et restauration

`backup.sh`/`backup-local.sh` archivent `dump.sql`/`dump_local.sql` + `.env` + logs. `restore.sh` restaure l'archive complète : recrée la base avec le **bon propriétaire** (`createdb -O <utilisateur>`, extrait du `.env` de l'archive) — depuis PostgreSQL 15, les droits `CREATE` sur le schéma `public` sont révoqués par défaut pour tout rôle autre que le propriétaire, un `createdb` sans `-O` (rôle `postgres` par défaut) fait donc échouer toute migration Flyway ultérieure avec `droit refusé pour le schéma public`. Restaure aussi le `.env` de l'archive et réaligne le mot de passe PostgreSQL du rôle applicatif sur `SPRING_DATASOURCE_PASSWORD` qu'il contient — sans ce réalignement, l'application ne peut plus se connecter à sa propre base après une restauration sur une instance dont le mot de passe diffère (ex. instance neuve).

`scripts/restore-test.sh` (#748) : test de restauration à la demande, jamais automatisé en cron/CI. Séquence : `vzdump` snapshot de la prod (non disruptif) → `pct restore` en LXC temporaire (199) → réattribution réseau (MAC neuve + `ip=dhcp`, sinon le LXC restauré hérite de l'IP/MAC statique de la prod et provoque un conflit ARP pendant tout le test) → `restore.sh` → health checks (`:9090`/`:9091`, **pas** `:8080` — c'est le port applicatif/SPA, pas l'actuator) → destruction. `pct clone` est délibérément évité : il refuse de cloner un conteneur ayant un point de montage bind (`mp0`, le partage NAS de la prod, monté uniquement en profil `prod` de `provision.sh`) — `vzdump` l'exclut nativement (« not a volume »). Le LXC restauré hérite aussi du flag `protection` de la prod, à désactiver avant tout `pct destroy`.

**Jamais automatisé via Woodpecker** : le LXC Woodpecker (VLAN 20, `192.168.20.0/24`) n'a volontairement pas de route active vers le réseau de management Proxmox (`192.168.1.0/24`, gateway distincte `192.168.1.1`) — confirmé (route présente mais tout le trafic, y compris ICMP, y est filtré), cohérent avec le modèle default-deny inter-VLAN déjà en place ailleurs sur cette infra (ex. NFS VLAN20→VLAN10 nécessite une règle explicite). Percer cette frontière donnerait à un pipeline CI (code de dépendances tierces, images Docker) un accès root à l'hyperviseur entier — disproportionné face au risque de compromission d'un pipeline. `scripts/restore-test.sh` s'exécute donc uniquement à la demande, copié puis lancé directement sur Proxmox.

## Variables d'environnement — java/web/.env

```
DATABASE_URL=jdbc:postgresql://localhost/strapontin
APP_CONFIG_SECRET=<clé AES-256-GCM de chiffrement de app_config>
BACKUP_INTERNAL_SECRET=<secret Bearer protégeant POST /api/interne/backup-statut>
```

`BACKUP_INTERNAL_SECRET` (v2.2.2) : généré par `provision.sh`. `backup-local.sh` le lit dans `.env` et l'envoie via `Authorization: Bearer`. Absent → l'endpoint répond 403 (notifications de backup perdues, mais le dump continue).

## Configuration applicative (`app_config`)

Chiffrement AES-256-GCM, clé = `APP_CONFIG_SECRET`.
⚠️ Changer `APP_CONFIG_SECRET` → toutes les valeurs `app_config` illisibles.
⚠️ Changer les clés VAPID → supprimer `push_abonnements` d'abord.
Clés applicatives (`TICKETMASTER_API_KEY`, `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET`, `CONTACT_EMAIL`, `PUBLIC_BASE_URL`, `VAPID_*`) configurables depuis `/admin`.
`RESEND_WEBHOOK_SECRET` : clé de signature Svix pour l'endpoint `POST /api/webhooks/resend` (bounces email). À copier depuis le dashboard Resend → Webhooks.

Rate limiting TM : max 2 jobs simultanés (3 → HTTP 429). Quota TM persisté dans `app_config` (`TM_QUOTA_JSON`). `TicketmasterSource.fetchPage` mesure la durée réelle de l'appel HTTP en cas de 429 (Spike Arrest) — objective si le rejet survient après une latence réseau anormale (jitter) plutôt qu'immédiatement, sans changer le cadencement lui-même. Cadencement des appels HTTP (`fr.strapontin.sources.CadenceurAppels`) : implémentation en mémoire par défaut (`CadenceurAppelsMemoire`, `sources` reste volontairement sans dépendance JDBC), mais Ticketmaster est aussi appelé directement par le module web (recherche interactive de salle à l'ajout, test de clé API admin) — un verrou en mémoire ne coordonnerait pas deux processus indépendants. `CadenceurAppelsPartage` (implémentation dupliquée dans `web` et `worker`, chacun avec son propre `NamedParameterJdbcTemplate`) réserve atomiquement le prochain appel autorisé via `UPDATE ... RETURNING` sur la table `cadences_appels_externes` (une ligne par service externe cadencé), le verrou de ligne Postgres suffisant à sérialiser les écritures concurrentes sans transaction `SERIALIZABLE`.
`FetchArtistesBatchJob`, `FetchRegionJob`, `FetchSallesAllJob`, `RecalculerMatchesJob`, `ReconciliationNocturneJob` annotés `@DisallowConcurrentExecution`. `WatchdogWorkerService` (`@Scheduled`, côté web) : alerte email si worker inactif > 3 h. `AlerteLogsAdminService` (`@Scheduled` 15 min, côté web, v2.6.1 #765) : digest email sur nouvelles entrées `logs_admin` niveau `error`, curseur persisté dans `app_config` (`ALERTE_LOGS_ADMIN_CURSEUR`, pas en mémoire — survit aux redéploiements), n'avance qu'après envoi réussi.
`spring.quartz.wait-for-jobs-to-complete-on-shutdown=true` (v2.7.0, #886) : un déploiement pendant un cycle en cours attend sa fin plutôt que de le tuer silencieusement (`RAMJobStore` ne persiste aucun trigger). Borné par `TimeoutStopSec=90` (`strapontin-worker.service`) et `spring.lifecycle.timeout-per-shutdown-phase=80s` — nécessite que `TicketmasterSource`/`EventimSource` aient un timeout HTTP borné (#887, `sources.ClientHttpFactory`), sinon un hoquet réseau ferait pendre le déploiement.
`SuiviChroniciteService` (`worker`) : compte, par job/source, les cycles consécutifs en échec — persisté dans `app_config` (`FIABILITE_STREAKS_JSON`), remis à zéro dès qu'un cycle est propre. Au-delà de 3 cycles consécutifs, le message `logs_admin` est qualifié de « chronique » plutôt que traité comme un warn isolé à chaque occurrence — intégré aux deux points génériques de remontée de bilan (`WorkerStatsService.remonterBilan` pour `fetch:*`, `EnrichissementSallesService.remonterBilans` pour Overpass).
`WorkerFetchService.mettreAJourAbsences` (v2.8.4) : `FetchSallesAllJob` l'appelle désormais sur `salle_id` (code mort jusqu'ici, jamais atteint — aucun concert rattaché uniquement à une salle suivie ne voyait son compteur évoluer) ; `FetchRegionJob` (browse-only) met à jour les absences de toutes les salles déjà connues du lot de départements traité, indépendamment de tout suivi utilisateur (sans quoi un concert dont ni l'artiste, ni la salle, ni le département ne finissent par être suivis restait hors de portée de toute détection de péremption). `remonterEchecsLots` (v2.8.6, `WorkerFetchService`) : un lot en échec au sein d'un job multi-lots (`fetch:region`/`fetch:artistes:batch`/`fetch:salles:all`) est désormais journalisé dans `logs_admin` (niveau `error` si tous les lots ont échoué, `warn` sinon), indépendamment du résultat des autres lots — l'ancien simple `log.error` SLF4J restait invisible tant que le bilan agrégé du job restait positif grâce aux lots réussis.

## Authentification

Invite-only. Login par identifiant (insensible à la casse). Rôles : `user` | `admin`.
2FA TOTP optionnel pour tous les utilisateurs — enrollment via `/parametres/totp`, challenge automatique à la connexion si activé. Cap : 500 artistes / 200 salles par user.
Algorithme TOTP conforme RFC 6238 (HMAC-SHA1, 30 s, ±1 fenêtre, saisie tolérante aux espaces). Réinitialisation 2FA par un admin depuis `/admin` (bouton « Réinit. 2FA », endpoint `POST /api/admin/utilisateurs/{id}/reset-totp`) pour un compte bloqué. Succès et échecs d'auth (login, rate-limit, TOTP) consignés dans `logs_admin` (source `auth`). Rate-limit login : 15 tentatives / 15 min par IP (bucket4j → 429).
Spring Security form login → cookie `SESSION` (JDBC-backed, survit aux restarts, `Max-Age=2592000`, `HttpOnly`, `SameSite=Lax` — pas `Strict`, compatibilité Safari sur navigation entrante — configuré via `DefaultCookieSerializer`, pas via `application.properties`). Mots de passe hashés en bcrypt.
`session_appareils` associe un `appareil_id` opaque à chaque `SPRING_SESSION.SESSION_ID` (jamais le `session_id` réel côté client — un XSS qui lirait la liste ne peut pas usurper une session). `AppareilEnregistrementInterceptor` (pas le contrôleur de login) enregistre l'appareil au premier appel API _suivant_ la connexion, car Spring Session (JDBC) ne persiste la session qu'après que le login a déjà rendu sa réponse. `/parametres` (Compte) et `/admin` exposent la gestion des appareils/sessions.
Détails : [wiki Authentification](https://codeberg.org/Kwaite/strapontin/wiki/Authentification)

## Dédoublonnage inter-sources

Deux passes : exacte sur `(artiste_norm, date, ville_norm)`, fuzzy Levenshtein normalisé ≥ 0.85. Résolution UUID-first : `PersisterConcerts.resoudreIdentitesSources` consulte `salle_sources`/`artiste_sources` avant la réconciliation floue, absorbe les renommages de salle, upsert automatique des salles TM absentes. `core.Dedoublonner.heuresCompatibles` (v2.8.5) tolère un écart de 3 minutes entre deux heures avant de les considérer distinctes (fiches TM du même évènement de types `package`/`prestation`), très en dessous de tout écart matinée/soirée réel. `MapeurProduitEventim.extraireNomArtiste` (v2.8.5) normalise les espaces insécables/fines (U+00A0, U+202F) qu'Eventim place parfois autour du séparateur `" - "` du titre — sinon le titre entier (avec le suffixe de tournée) est retenu comme nom d'artiste. `sources.ResolveurNomCanonique.rechercherDeezerArtiste` (v2.8.5) : un candidat Deezer dont le nom normalisé correspond exactement au nom recherché l'emporte toujours sur un homonyme approximatif mieux référencé (nb de fans) — la popularité ne départage plus qu'entre candidats eux-mêmes exacts.

`estDoublonSalle` (`core.CorrespondanceSalle`) : Levenshtein ≥ 0.75 ou containment de caractères | Jaccard tokens spécifiques > 0.5 | token pivot spécifique (≥ 7 chars, Jaccard > 0.3) | égalité sans espaces (couvre une source qui omet l'apostrophe, ex. "LOlympia"/"L'Olympia") | containment de tous les tokens spécifiques du nom le plus court dans le plus long (≥ 4 caractères/token, ≥ 2 tokens spécifiques de chaque côté). "Tokens spécifiques" = tokens significatifs moins `MOTS_GENERIQUES_SALLE` (theatre, chateau, casino, colisee, expositions, culturel, metropole, municipal, antique, parc, barriere, eglise, saint… — "arena" volontairement absent, contributeur légitime ; "eglise"/"saint" ajoutés en v2.8.4, partagés par la quasi-totalité des édifices religieux, gonflaient à tort le Jaccard entre deux églises distinctes). Limites connues non couvertes : pivot nom de ville, Jaccard gonflé par un token court comme "des". `estDoublonSalle(a, b, pivotAutorise)` : `pivotAutorise=false` désactive à la fois le pivot et le containment de caractères (v2.8.4, le premier critère) — les deux plus faibles des cinq, un nom court peut être préfixe strict d'un nom plus long sans rapport (ex. "la prade"/"la pradella") — réservé aux cas sans aucun signal de localisation indépendant (voir `WikidataSalleSource`).

`estDoublonArtiste` : Jaro ≥ 0.95 | containment ratio ≥ 0.65. `normaliserTexte` : `$` supprimé sans espace, `&` → `and`.

`ResolveurSalleParConcert.chercherSalleParTokens`/`raccrocherSallesParNomNorm` : filtre dept avec repli sur le département réel des concerts déjà rattachés quand `salles.dept` est vide (évite les homonymes inter-villes) — les deux méthodes doivent partager ce filtre, sinon l'une défait silencieusement la protection de l'autre. Parmi les candidats validés par `estDoublonSalle`, `chercherSalleParTokens` retient celui au Jaccard de tokens le plus élevé plutôt que le premier de la liste (v2.8.4, l'ordre SQL n'est pas garanti) — un nom générique de complexe multi-salles (ex. "La Seine Musicale - Boulogne Billancourt") peut valider plusieurs salles physiquement distinctes du même complexe via le seul pivot. `ReconciliationNomsSalles` (worker) inclut `dept` et l'heure (précision minute) dans la clé de réconciliation intra-lot/inter-jobs, en plus de `artiste_norm`/`date`. `ReconciliateurSallesOrphelines.retenterSallesOrphelines()` (nocturne) retente la résolution par nom des concerts dont `salle_id` est resté `NULL` à la persistance initiale — candidats (toutes les salles) chargés en une seule requête et scorés en mémoire (v2.8.7, corrige un N+1 SQL par concert orphelin). `chercherSalleParCleForte` (v2.8.6) filtre de même ses candidats par `deptsConnus` avant de choisir — un doublon de concert déjà mal rattaché (dept de sa salle incohérent) pouvait sinon se reconfirmer lui-même via ce repli, l'ancien `LIMIT 1` sans `ORDER BY` retournant indifféremment la bonne ou la mauvaise salle ; retourne `null` (log warn) si aucun candidat n'est géographiquement cohérent plutôt que de deviner.
→ Détails et justification des seuils : [wiki Sources-de-données](https://codeberg.org/Kwaite/strapontin/wiki/Sources-de-donn%C3%A9es)
