# Jobs background (Quartz)

Paradigme : **pré-fetch en arrière-plan, jamais d'appel API depuis le browser**.

Rate limiting TM : max 2 jobs simultanés (3 → HTTP 429). Quota TM persisté dans `app_config` (`TM_QUOTA_JSON`, `GestionQuotaTM`) — 3 seuils : `SEUIL_QUOTA_WARN=200` (avertissement), `SEUIL_QUOTA_CRON=500` (jobs cron suspendus en dessous), `SEUIL_QUOTA_ABORT=50` (tous les jobs TM annulés en dessous). `lireQuota` : si le timestamp `Rate-Limit-Reset` (ms, fourni par TM) est dépassé, retourne un quota synthétique `dispo = total` et persiste cette mise à jour pour débloquer les jobs cron sans attendre le prochain vrai appel TM (qui réécrira la valeur réelle depuis les headers). `TicketmasterSource.fetchPage` mesure la durée réelle de l'appel HTTP en cas de 429 (Spike Arrest) — objective si le rejet survient après une latence réseau anormale (jitter) plutôt qu'immédiatement, sans changer le cadencement lui-même. Cadencement des appels HTTP (`fr.strapontin.sources.CadenceurAppels`) : implémentation en mémoire par défaut (`CadenceurAppelsMemoire`, `sources` reste volontairement sans dépendance JDBC), mais Ticketmaster est aussi appelé directement par le module web (recherche interactive de salle à l'ajout, test de clé API admin) — un verrou en mémoire ne coordonnerait pas deux processus indépendants. `CadenceurAppelsPartage` (implémentation dupliquée dans `web` et `worker`, chacun avec son propre `NamedParameterJdbcTemplate`) réserve atomiquement le prochain appel autorisé via `UPDATE ... RETURNING` sur la table `cadences_appels_externes` (une ligne par service externe cadencé), le verrou de ligne Postgres suffisant à sérialiser les écritures concurrentes sans transaction `SERIALIZABLE`.
`FetchArtistesBatchJob`, `FetchRegionJob`, `FetchSallesAllJob`, `RecalculerMatchesJob`, `ReconciliationNocturneJob` annotés `@DisallowConcurrentExecution`. `WatchdogWorkerService` (`@Scheduled`, côté web) : alerte email si worker inactif > 3 h. `AlerteLogsAdminService` (`@Scheduled` 15 min, côté web, v2.6.1 #765) : digest email sur nouvelles entrées `logs_admin` niveau `error`, curseur persisté dans `app_config` (`ALERTE_LOGS_ADMIN_CURSEUR`, pas en mémoire — survit aux redéploiements), n'avance qu'après envoi réussi. `LogAdminService.lireErreursDepuis` plafonne désormais le lot lu (`LIMITE_ERREURS_DEPUIS`, v2.8.7) — un retard important (destinataire d'alerte absent plusieurs cycles) est absorbé sur plusieurs digests successifs plutôt que de charger un lot non borné, sans perte grâce à l'avancée du curseur.
`spring.quartz.wait-for-jobs-to-complete-on-shutdown=true` (v2.7.0, #886) : un déploiement pendant un cycle en cours attend sa fin plutôt que de le tuer silencieusement (`RAMJobStore` ne persiste aucun trigger). Borné par `TimeoutStopSec=90` (`strapontin-worker.service`) et `spring.lifecycle.timeout-per-shutdown-phase=80s` — nécessite que `TicketmasterSource`/`EventimSource` aient un timeout HTTP borné (#887, `sources.ClientHttpFactory`), sinon un hoquet réseau ferait pendre le déploiement.
`SuiviChroniciteService` (`worker`) : compte, par job/source, les cycles consécutifs en échec — persisté dans `app_config` (`FIABILITE_STREAKS_JSON`), remis à zéro dès qu'un cycle est propre. Au-delà de 3 cycles consécutifs, le message `logs_admin` est qualifié de « chronique » plutôt que traité comme un warn isolé à chaque occurrence — intégré aux deux points génériques de remontée de bilan (`WorkerStatsService.remonterBilan` pour `fetch:*`, `EnrichissementSallesService.remonterBilans` pour Overpass).
`WorkerFetchService.executerFetchSallesAll` (`fetch:salles:all`) est restreint aux salles réellement suivies par un utilisateur (`user_salles`) — un artiste suivi jouant dans une salle non suivie est de toute façon déjà détecté par `fetch:artistes:batch` (recherche nationale par nom, indépendante du département). Avant cette restriction, toutes les salles du référentiel avec source TM étaient refetchées à chaque cycle (255 en prod le 18/07/2026), épuisant le quota TM en une seule journée. `WorkerFetchCommun.mettreAJourAbsences` (v2.8.4, extrait de `WorkerFetchService` dans `WorkerFetchCommun` en 2.9.1) : `FetchSallesAllJob` l'appelle désormais sur `salle_id` (code mort jusqu'ici, jamais atteint — aucun concert rattaché uniquement à une salle suivie ne voyait son compteur évoluer) ; `FetchRegionJob` (browse-only) met à jour les absences de toutes les salles déjà connues du lot de départements traité, indépendamment de tout suivi utilisateur (sans quoi un concert dont ni l'artiste, ni la salle, ni le département ne finissent par être suivis restait hors de portée de toute détection de péremption). `remonterEchecsLots` (v2.8.6, même extraction) : un lot en échec au sein d'un job multi-lots (`fetch:region`/`fetch:artistes:batch`/`fetch:salles:all`) est désormais journalisé dans `logs_admin` (niveau `error` si tous les lots ont échoué, `warn` sinon), indépendamment du résultat des autres lots — l'ancien simple `log.error` SLF4J restait invisible tant que le bilan agrégé du job restait positif grâce aux lots réussis. `FetchArtistesBatchExecutor` (v3.0.0) distingue désormais une panne réseau transitoire (DNS, I/O, timeout — `java.io.IOException` et sous-classes, y compris en cause imbriquée) d'un échec applicatif lors du fetch TM/Eventim par lot : la première est propagée à `remonterEchecsLots`/`RetryLotsService` même quand elle est absorbée par un simple `catch` interne (jusqu'ici un `LOG.warn` sans remontée, `remonterEchecsLots` recevait alors systématiquement une liste vide malgré un lot réellement en échec), la seconde reste un échec silencieux ordinaire (non retenté automatiquement).
