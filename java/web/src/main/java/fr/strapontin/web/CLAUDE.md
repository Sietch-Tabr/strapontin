# Module web (`fr.strapontin.web`)

**Pagination admin** (v2.8.7) : `ReferentielSallesService`/`ReferentielArtistesService` (`page`/`totalPages`/`total`, `COUNT(*) OVER()` calculé dans la même exécution que la page plutôt qu'un `COUNT(*)` séparé, repli sur un second `COUNT` uniquement si la page demandée dépasse le total) — même pattern désormais étendu à `AdminService.listerUtilisateurs`, `ConcertsAdminService.lister` et `SourcesService.listerSalles` (endpoint dédié `GET /api/admin/sources/salles`, recherche par nom et bascule avec lieu Eventim/sans source côté serveur — `GET /api/admin/sources` ne renvoie plus que les statuts de sources).

**Sécurité admin/sessions** : `AdminService`/`SetupService`/`PushService`/`SalleService` isolent leurs opérations sensibles en transaction `SERIALIZABLE` (`REQUIRES_NEW`/`NESTED`) + retry, via auto-injection par setter (`@Autowired setSelf(@Lazy X self)`, pas par constructeur — évite l'auto-référence en test).
⚠️ **Ne jamais appeler une méthode `REQUIRES_NEW`+`SERIALIZABLE` depuis une transaction déjà ouverte** — épuisement garanti du pool HikariCP (incident réel). `AdminService.modifierUtilisateur` (`PATCH`) refuse donc toute rétrogradation d'admin, seule ou combinée : elle passe uniquement par `POST /api/admin/utilisateurs/{id}/revoquer-admin` (révocation différée avec préavis).
`WorkerRevocationService.executerRevoquerAdmins` (job `revoquer:admins`, worker) passe `admin` à `user` pour tout compte dont `revocation_admin_le` est dans le passé, puis révoque ses sessions actives — sans quoi l'admin rétrogradé resterait authentifié avec son ancien rôle (chargé en session à la connexion, jamais rafraîchi) jusqu'à expiration naturelle (30 jours). Le module worker n'a pas le bean `FindByIndexNameSessionRepository` (spécifique à Spring Session côté web) : suppression directe des lignes `SPRING_SESSION` par `PRINCIPAL_NAME`.
Les trois points de construction d'URL de base pour un lien envoyé par email (`PasswordResetController`, `ParametresRestController`, `AdminController`) refusent tous l'envoi (503/blocage silencieux selon le flux) si `PUBLIC_BASE_URL` n'est pas configurée, plutôt que de se rabattre sur le header `Host` de la requête entrante (Host Header Injection). `users.two_factor_secret` chiffré (v2.8.7, `ConfigCipher`/`APP_CONFIG_SECRET`, même mécanisme qu'`app_config`) plutôt qu'en clair — lecture avec repli sur la valeur brute en cas d'échec de déchiffrement (comptes déjà enrôlés avant le chiffrement).

`IntegriteAlerteController`/`BackupAlerteController` (`web.email`) : endpoints internes protégés par secret partagé (`INTEGRITY_INTERNAL_SECRET`/`BACKUP_INTERNAL_SECRET`, header `Authorization: Bearer`, comparaison `MessageDigest.isEqual`) appelés par `scripts/aide-check.sh`/`backup-local.sh` — flux `strapontin-integrity.timer` (quotidien 04h) → `aide --check` → `POST /api/interne/integrite-statut` → `logs_admin` (`info`/`error`) → `EmailAlerteService.envoyerAlerteIntegrite` sur modification détectée, détail : [wiki Sécurité](https://codeberg.org/Kwaite/strapontin/wiki/Sécurité).

`VapidKeyGenerator` (`fr.strapontin.web`, v2.8.7) : génération de clé EC P-256 partagée entre `SetupService` (première génération) et `VapidService` (régénération admin) — dupliquée verbatim auparavant.

**Bean Validation** : tout endpoint `@RequestBody` prend un DTO record annoté (`@NotBlank`/`@Size`/etc.) + `@Valid` — jamais de `Map<String,String>` brut. `@Valid` ne s'exerce que via le pipeline Spring MVC réel, jamais sur un appel Java direct : tester la validation via `Validator.validate(new Record(...))` (pattern `RequeteXxxValidationTest`). Exceptions documentées : `ForgotPasswordRequest` (anti-énumération), `ClientController` (bag ouvert borné autrement), `ResendWebhookController` (payload signé Svix).

⚠️ **`@ModelAttribute` sur un record avec un champ primitif (`int`/`boolean`)** : un paramètre de requête absent laisse le champ à `null`, et la conversion Spring vers le type primitif échoue avant même l'exécution du constructeur compact (`Failed to convert value of type 'null' to required type 'int'`) — `@RequestParam(defaultValue = ...)` sur le composant du record n'a **aucun effet** dans ce chemin de binding (contrairement à un paramètre de méthode de contrôleur classique, vérifié par test négatif avant conclusion, v2.9.1). Toujours utiliser un type boîte (`Integer`/`Boolean`) et restituer le défaut dans le constructeur compact, comme les champs `String` du même record (`FiltreConcerts.page`/`quinzaine`/`masques`, bug réel trouvé par le run E2E complet — tout appel omettant un seul de ces paramètres échouait en 400 sur `/api/spectacles` et `/api/decouverte`).

Authentification/sessions détaillées : [`securite/CLAUDE.md`](securite/CLAUDE.md).

**Communication d'incident** (v3.0.1, package `incident`) : `IncidentService.publier` (onglet admin Bannière) enregistre une communication unique active (`communications_incident`, la précédente est close), affichée par `BanniereIncident.vue` sur toutes les pages y compris `/login` (`GET /api/incident` en `permitAll`, masquage par utilisateur en `localStorage`). Canaux optionnels : un email par compte (refusé d'emblée si le quota Resend restant ne couvre pas tous les comptes — un envoi partiel laisserait des comptes sans nouvelles sans savoir lesquels), push à tous les abonnés, changement de mot de passe forcé (`users.changement_mdp_force_le`) : publication = révocation de toutes les sessions sauf celle de l'admin qui publie, puis connexion refusée en 403 `reinitialisation_requise` après vérification du mot de passe (`VerificationMotDePasseExige`, post-check du `DaoAuthenticationProvider`) tant que le mot de passe n'a pas été réinitialisé par email — seule `VerificationRepository` (lien reçu par email, preuve de possession de la boîte) lève l'exigence, jamais un changement depuis les paramètres (le mot de passe actuel a pu fuiter). Prévenir avant toute régénération des clés VAPID (invalide tous les abonnements push).

**Décisions admin sur signalements de salles** (v3.0.1) : `SignalementsAdminService.accepterContamination` (`salle_sources.contamination_acceptee_le`) et `declarerSallesDistinctes` (`salles_paires_distinctes`, `CHECK salle_a < salle_b` — paire ordonnée par l'ordre textuel des UUID, l'ordre `UUID.compareTo` Java diffère de celui de PostgreSQL) mémorisent un faux positif pour que `CoherenceMultiSalleService` ne le re-signale plus. `salles.doublon_signale` est une FK `ON DELETE SET NULL` (plus de référence pendante après fusion).

**Resend — quota et anti-boucle** : Garde-fou de quota jour/mois dupliqué web (`web.email.GestionQuotaResend`, alerte 80% via `AlerteQuotaResendService`) et worker (`worker.quota.GestionQuotaResendWorker`, blocage effectif à 100/3000 — digest email suspendu, `logs_admin error` capté par `AlerteLogsAdminService`) — même clé `app_config` (`RESEND_QUOTA_JSON`) lue/écrite en clair par les deux, `ConfigServiceWorker` étant explicitement en lecture seule côté worker ; COUNT+INSERT du compteur rendu atomique par une transaction `SERIALIZABLE`+retry (même pattern que `web.push.PushService.abonner`), sans quoi deux cycles de digest concurrents pourraient tous deux réserver un envoi au-delà du quota réel Resend (côté worker uniquement, où la concurrence intra-JVM est réelle) — entre web et worker (deux JVM séparées), le compteur reste best-effort : une race read-increment-write non atomique peut sous-compter, jamais sur-bloquer dangereusement, risque assumé pour un projet mono-instance. `AlerteQuotaResendService` (`@Scheduled` 15 min) alerte au franchissement du seuil 80%, après recalage du compteur local sur l'usage réel Resend (`GET /usage`, `EmailSender.recalerQuotaSurUsageReel`, maximum local/réel — un envoi hors application reste sinon invisible) — état "déjà signalé" porté par le compteur partagé lui-même (`alerteJourEnvoyee`/`alerteMoisEnvoyee`, remis à `false` au rollover jour/mois), pas un curseur séparé comme `AlerteLogsAdminService`. `EmailAlerteService.envoyerNotificationBounce`/`envoyerNotificationPlainteSpam` throttlées à 1 envoi/heure/type (`app_config`, survit aux redéploiements) — garde-fou anti-boucle suite à l'incident du 15/07/2026 (#907, quota journalier épuisé en 14 minutes par une boucle de bounces sans garde-fou local), détail : [wiki Notifications-email](https://codeberg.org/Kwaite/strapontin/wiki/Notifications-email). `EmailSender.obtenirDestinataireAlerte` résout `ADMIN_ALERT_EMAIL` (`app_config`) puis, à défaut, le premier admin créé — jamais de repli sur `CONTACT_EMAIL`/l'expéditeur, c'est précisément cette confusion qui a causé la boucle du 15/07/2026.

`SalleRechercheNominatimService` (web, extrait de `SalleService` en v2.9.1) : détail du filtre de pertinence `TYPES_SALLE_NOMINATIM` déjà documenté, [wiki Sources-de-données](https://codeberg.org/Kwaite/strapontin/wiki/Sources-de-donn%C3%A9es).

**Push web et comptes (3.0.3)** : `NotificationPushService` renvoie un `ResultatEnvoiPush` (raison et message en français courant, `POST /api/push/tester` → statut correspondant) ; test d'envoi réel `NotificationPushEnvoiReelTest` (vraies clés, seul le transport HTTP intercepté). `GET /api/user/config/canal-perdu` alimente `BandeauCanalPerdu.vue`. Une ligne `user_config` est créée à chaque création de compte (défauts V83 : email hebdomadaire des artistes) ; sans elle le digest ignorait le compte. Identifiant : règle unique `securite.RegleIdentifiant` (3 à 30, minuscules, `[a-z0-9._-]`) pour setup, invitation et changement. Messages du worker injoignable/en erreur : `WorkerProxyService.MESSAGE_INJOIGNABLE`/`MESSAGE_EN_ERREUR`, sans code de statut.
