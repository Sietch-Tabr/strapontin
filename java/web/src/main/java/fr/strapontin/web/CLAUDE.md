# Module web (`fr.strapontin.web`)

**Pagination admin** (v2.8.7) : `ReferentielSallesService`/`ReferentielArtistesService` (`page`/`totalPages`/`total`, `COUNT(*) OVER()` calculé dans la même exécution que la page plutôt qu'un `COUNT(*)` séparé, repli sur un second `COUNT` uniquement si la page demandée dépasse le total) — même pattern désormais étendu à `AdminService.listerUtilisateurs`, `ConcertsAdminService.lister` et `SourcesService.listerSalles` (endpoint dédié `GET /api/admin/sources/salles`, recherche par nom et bascule avec lieu Eventim/sans source côté serveur — `GET /api/admin/sources` ne renvoie plus que les statuts de sources).

**Sécurité admin/sessions** : `AdminService`/`SetupService`/`PushService`/`SalleService` isolent leurs opérations sensibles en transaction `SERIALIZABLE` (`REQUIRES_NEW`/`NESTED`) + retry, via auto-injection par setter (`@Autowired setSelf(@Lazy X self)`, pas par constructeur — évite l'auto-référence en test).
⚠️ **Ne jamais appeler une méthode `REQUIRES_NEW`+`SERIALIZABLE` depuis une transaction déjà ouverte** — épuisement garanti du pool HikariCP (incident réel). `AdminService.modifierUtilisateur` (`PATCH`) refuse donc toute rétrogradation d'admin, seule ou combinée : elle passe uniquement par `POST /api/admin/utilisateurs/{id}/revoquer-admin` (révocation différée avec préavis).
`WorkerRevocationService.executerRevoquerAdmins` (job `revoquer:admins`, worker) passe `admin` à `user` pour tout compte dont `revocation_admin_le` est dans le passé, puis révoque ses sessions actives — sans quoi l'admin rétrogradé resterait authentifié avec son ancien rôle (chargé en session à la connexion, jamais rafraîchi) jusqu'à expiration naturelle (30 jours). Le module worker n'a pas le bean `FindByIndexNameSessionRepository` (spécifique à Spring Session côté web) : suppression directe des lignes `SPRING_SESSION` par `PRINCIPAL_NAME`.
Les trois points de construction d'URL de base pour un lien envoyé par email (`PasswordResetController`, `ParametresRestController`, `AdminController`) refusent tous l'envoi (503/blocage silencieux selon le flux) si `PUBLIC_BASE_URL` n'est pas configurée, plutôt que de se rabattre sur le header `Host` de la requête entrante (Host Header Injection). `users.two_factor_secret` chiffré (v2.8.7, `ConfigCipher`/`APP_CONFIG_SECRET`, même mécanisme qu'`app_config`) plutôt qu'en clair — lecture refusée (secret `null`, `ERROR` journalisé) si le déchiffrement échoue ; un secret resté en clair (Base32 brut, comptes enrôlés avant le chiffrement) est chiffré à chaque démarrage par `RechiffrementSecretConfig`, et l'invariant nocturne `secret_totp_non_chiffre` le signale.

`IntegriteAlerteController`/`BackupAlerteController` (`web.email`) : endpoints internes protégés par secret partagé (`INTEGRITY_INTERNAL_SECRET`/`BACKUP_INTERNAL_SECRET`, header `Authorization: Bearer`, comparaison `MessageDigest.isEqual`) appelés par `scripts/aide-check.sh`/`backup-local.sh` — flux `strapontin-integrity.timer` (quotidien 04h) → `aide --check` → `POST /api/interne/integrite-statut` → `logs_admin` (`info`/`error`) → `EmailAlerteService.envoyerAlerteIntegrite` sur modification détectée, détail : [wiki Sécurité](https://github.com/Sietch-Tabr/strapontin/wiki/Sécurité).

`VapidKeyGenerator` (`fr.strapontin.web`, v2.8.7) : génération de clé EC P-256 partagée entre `SetupService` (première génération) et `VapidService` (régénération admin) — dupliquée verbatim auparavant.

**Bean Validation** : tout endpoint `@RequestBody` prend un DTO record annoté (`@NotBlank`/`@Size`/etc.) + `@Valid` — jamais de `Map<String,String>` brut. `@Valid` ne s'exerce que via le pipeline Spring MVC réel, jamais sur un appel Java direct : tester la validation via `Validator.validate(new Record(...))` (pattern `RequeteXxxValidationTest`). Exceptions documentées : `ForgotPasswordRequest` (anti-énumération), `ClientController` (bag ouvert borné autrement), `ResendWebhookController` (payload signé Svix).

⚠️ **`@ModelAttribute` sur un record avec un champ primitif (`int`/`boolean`)** : un paramètre de requête absent laisse le champ à `null`, et la conversion Spring vers le type primitif échoue avant même l'exécution du constructeur compact (`Failed to convert value of type 'null' to required type 'int'`) — `@RequestParam(defaultValue = ...)` sur le composant du record n'a **aucun effet** dans ce chemin de binding (contrairement à un paramètre de méthode de contrôleur classique, vérifié par test négatif avant conclusion, v2.9.1). Toujours utiliser un type boîte (`Integer`/`Boolean`) et restituer le défaut dans le constructeur compact, comme les champs `String` du même record (`FiltreConcerts.page`/`quinzaine`/`masques`, bug réel trouvé par le run E2E complet — tout appel omettant un seul de ces paramètres échouait en 400 sur `/api/spectacles` et `/api/decouverte`).

Authentification/sessions détaillées : [`securite/CLAUDE.md`](securite/CLAUDE.md).

**Communication d'incident** (v3.0.1, package `incident`) : `IncidentService.publier` (onglet admin Bannière) enregistre une communication unique active (`communications_incident`, la précédente est close), affichée par `BanniereIncident.vue` sur toutes les pages y compris `/login` (`GET /api/incident` en `permitAll`, masquage par utilisateur en `localStorage`). Canaux optionnels : un email par compte (refusé d'emblée si le quota Resend restant ne couvre pas tous les comptes — un envoi partiel laisserait des comptes sans nouvelles sans savoir lesquels), push à tous les abonnés, changement de mot de passe forcé (`users.changement_mdp_force_le`) : publication = révocation de toutes les sessions sauf celle de l'admin qui publie, puis connexion refusée en 403 `reinitialisation_requise` après vérification du mot de passe (`VerificationMotDePasseExige`, post-check du `DaoAuthenticationProvider`) tant que le mot de passe n'a pas été réinitialisé par email — seule `VerificationRepository` (lien reçu par email, preuve de possession de la boîte) lève l'exigence, jamais un changement depuis les paramètres (le mot de passe actuel a pu fuiter). Prévenir avant toute régénération des clés VAPID (invalide tous les abonnements push).

**Décisions admin sur signalements de salles** (v3.0.1) : `SignalementsAdminService.accepterContamination` (`salle_sources.contamination_acceptee_le`) et `declarerSallesDistinctes` (`salles_paires_distinctes`, `CHECK salle_a < salle_b` — paire ordonnée par l'ordre textuel des UUID, l'ordre `UUID.compareTo` Java diffère de celui de PostgreSQL) mémorisent un faux positif pour que `CoherenceMultiSalleService` ne le re-signale plus. `salles.doublon_signale` est une FK `ON DELETE SET NULL` (plus de référence pendante après fusion).

**Resend — quota et anti-boucle** : Garde-fou de quota jour/mois dupliqué web (`web.email.GestionQuotaResend`, alerte 80% via `AlerteQuotaResendService`) et worker (`worker.quota.GestionQuotaResendWorker`, blocage effectif à 100/3000 — digest email suspendu, `logs_admin error` capté par `AlerteLogsAdminService`) — même clé `app_config` (`RESEND_QUOTA_JSON`) lue/écrite en clair par les deux, `ConfigServiceWorker` étant explicitement en lecture seule côté worker ; COUNT+INSERT du compteur rendu atomique par une transaction `SERIALIZABLE`+retry (même pattern que `web.push.PushService.abonner`), sans quoi deux cycles de digest concurrents pourraient tous deux réserver un envoi au-delà du quota réel Resend (côté worker uniquement, où la concurrence intra-JVM est réelle) — entre web et worker (deux JVM séparées), le compteur reste best-effort : une race read-increment-write non atomique peut sous-compter, jamais sur-bloquer dangereusement, risque assumé pour un projet mono-instance. `AlerteQuotaResendService` (`@Scheduled` 15 min) alerte au franchissement du seuil 80%, après recalage du compteur local sur l'usage réel Resend (`GET /usage`, `EmailSender.recalerQuotaSurUsageReel`, maximum local/réel — un envoi hors application reste sinon invisible) — état "déjà signalé" porté par le compteur partagé lui-même (`alerteJourEnvoyee`/`alerteMoisEnvoyee`, remis à `false` au rollover jour/mois), pas un curseur séparé comme `AlerteLogsAdminService`. `EmailAlerteService.envoyerNotificationBounce`/`envoyerNotificationPlainteSpam` throttlées à 1 envoi/heure/type (`app_config`, survit aux redéploiements) — garde-fou anti-boucle suite à l'incident du 15/07/2026 (#907, quota journalier épuisé en 14 minutes par une boucle de bounces sans garde-fou local), détail : [wiki Notifications-email](https://github.com/Sietch-Tabr/strapontin/wiki/Notifications-email). `EmailSender.obtenirDestinataireAlerte` résout `ADMIN_ALERT_EMAIL` (`app_config`) puis, à défaut, le premier admin créé — jamais de repli sur `CONTACT_EMAIL`/l'expéditeur, c'est précisément cette confusion qui a causé la boucle du 15/07/2026.

`SalleRechercheNominatimService` (web, extrait de `SalleService` en v2.9.1) : détail du filtre de pertinence `TYPES_SALLE_NOMINATIM` déjà documenté, [wiki Sources-de-données](https://github.com/Sietch-Tabr/strapontin/wiki/Sources-de-donn%C3%A9es).

Référentiel admin (`ReferentielSallesService`/`ReferentielArtistesService`, fusion, `ignorerIntervention`) : détail dans [`worker…/sante/CLAUDE.md`](../../../../../../../worker/src/main/java/fr/strapontin/worker/sante/CLAUDE.md).

**Push web et comptes (3.0.3)** : `NotificationPushService` renvoie un `ResultatEnvoiPush` (raison et message en français courant, `POST /api/push/tester` → statut correspondant) ; test d'envoi réel `NotificationPushEnvoiReelTest` (vraies clés, seul le transport HTTP intercepté). `GET /api/user/config/canal-perdu` (`canalPerdu`, `pushJamaisActive`) alimente `BandeauCanalPerdu.vue` ; `GET /api/user/config/departements-sans-concert` signale dans Paramètres et Découverte un département choisi sans aucun concert à venir. Accueil et Mes spectacles renvoient l'inclusion effective des indisponibles (préférence comprise) et leur nombre (`FiltreConcertsBuilder.CONDITION_DISPONIBLE`), le front envoie toujours une valeur explicite (`utils/filtreIndisponibles.js`). Une ligne `user_config` est créée à chaque création de compte (défauts V83 : email hebdomadaire des artistes) ; sans elle le digest ignorait le compte. Identifiant : règle unique `securite.RegleIdentifiant` (3 à 30, minuscules, `[a-z0-9._-]`) pour setup, invitation et changement. Messages du worker injoignable/en erreur : `WorkerProxyService.MESSAGE_INJOIGNABLE`/`MESSAGE_EN_ERREUR`, sans code de statut.

Fréquence « jamais » (3.0.5) : elle coupe aussi le push. `UserConfigService.majNotifications` et l'import de préférences (`PreferencesService.importerConfig`) forcent `notif_artistes_push`/`notif_salles_push` à `false` (`UserConfigService.pushPermis`), `V88` aligne les comptes existants ; sans cela, ni la livraison, ni le contrôle des canaux perdus (`frequence_notifications <> 'jamais'`) ne traitaient ce compte.

**Limitation de débit (3.0.6)** : un seul mécanisme, `securite.LimiteurDebit` (fenêtre glissante : journal d'horodatages par clé dans un cache Caffeine, le plafond annoncé est vrai sur toute période de la durée de la fenêtre ; bucket4j retiré). Clés : `AdresseClient.cle` (IPv4 telle quelle, IPv6 ramenée à son préfixe /64) pour les points sans compte, l'identifiant utilisateur sinon (signalements aide et salle : 3 par heure par utilisateur). Connexion : 15 essais/15 min par adresse et 10 mots de passe faux/15 min par compte quelle que soit l'adresse (`AuthController`, 429 par `ErreurMetier`, `warn` dans `logs_admin` au seuil, remis à zéro au succès). Mot de passe oublié : 3 demandes/h par adresse, ignorées sans rien révéler. Changement d'email : 3/h par compte et 2/jour par destinataire. Changement de mot de passe et désactivation du TOTP : 5 échecs/15 min par utilisateur. Recherches d'artistes et de salles (`BudgetRecherchesExternes`) : 15 par minute par utilisateur et plafond global par minute et par service externe (Nominatim 20, Wikidata 60, Deezer 60, `warn` dans `logs_admin` toutes les 10 min au plus) ; l'appel Nominatim attend en plus son créneau de `cadences_appels_externes` (partagé avec le worker). `server.tomcat.remoteip.internal-proxies` (profil prod) ne fait confiance à `X-Forwarded-For` que du proxy inverse (Nginx Proxy Manager, 192.168.20.98) et de la boucle locale : par défaut Tomcat l'accepte de toute adresse privée, donc d'un poste du réseau local joignant le port 8080. Si l'adresse du proxy change, la mettre à jour (tous les clients partageraient sinon une même limite).

**Push (3.0.6)** : `PushService.abonner` nomme l'appareil (`securite.NomAppareil`, depuis le User-Agent et l'en-tête `X-Mode-Affichage`), `AbonnementDto` expose `enEchecDepuis` et `cause` (`EchecPush.causeLisible`), `VapidService.genererVapid(motif)` exige un motif et prévient par email les comptes concernés (`nbComptesPrevenus`/`nbComptesNonPrevenus`). `ResendWebhooksAdminService` (admin) : liste/rejoue un événement webhook Resend en échec (`Webhooks.listEvents`/`replayEvent`, resend-java 4.23.0) — le `webhookId` n'est jamais configuré explicitement, résolu à chaque appel en filtrant `webhooks().list()` sur l'endpoint `PUBLIC_BASE_URL + "/api/webhooks/resend"` déjà connu.

**3.1.0** : `SourcesService` liste chaque site de salle (`site_salle:<site>`, préfixe de `salle_sources.identifiant_externe`) avec ses salles, son dernier passage propre (`MAX(observations.updated_at)` de la source) et un `etat` ; une source ajoutée apparaît dès sa première salle, `SourcesServiceIntegrationTest` échoue si une source observée manque. `ActiviteUtilisateurInterceptor` marque l'activité par un cache Caffeine (un jour par utilisateur) et non par un attribut de session : deux requêtes parallèles d'une session neuve écrivaient la même clé de `SPRING_SESSION_ATTRIBUTES`. « Annuler (garder) » (`ConcertsAdminService.annulerSuppression`) pose `evenements.maintenu_le` (V99) : la fiche n'est plus jamais signalée à supprimer. `WorkerTriggerUtils.declencherWorkerAsync` prend un gabarit d'adresse et des variables. L'email d'invitation invite à rejoindre Strapontin (HTML et texte brut identiques). `ClientController` garde jusqu'à 2000 caractères de `pile` (pile d'appel envoyée par `utils/erreursClient.js`).

**3.1.1** : `securite.NomAppareil` (navigateur, système, mode `pwa`/`navigateur`) est la source unique du nom d'appareil (email de nouvelle connexion avec le User-Agent brut en petit, liste des sessions, abonnés push) et de la comparaison `AppareilsService.estNouvelAppareil` : une mise à jour du navigateur ou du système ne déclenche plus d'alerte, un navigateur, un système ou un mode jamais vus en déclenchent une (`session_appareils.mode_affichage`, V100 ; `NULL` des sessions antérieures compatible avec tout mode). Le front annonce son mode par `X-Mode-Affichage` sur chaque appel (`utils/modeAffichage.js`). Limites connues, sans modèle d'appareil : un iPad récent se présente comme un Mac, Windows 10 et 11 se confondent. Retrait du dernier appareil push (révocation, retrait manuel, rotation VAPID) : `EchecPush.SQL_DECOCHER_PUSH_SANS_APPAREIL` décoche les contenus push (et passe la fréquence à `jamais` si aucun contenu email ne reste), `AvertissementCanalPerduService` prévient par email quels que soient les autres canaux, `UserConfigService.canalNotificationPerdu` ne dépend plus des cases. Un nouvel abonnement efface le retrait (`SQL_EFFACER_RETRAIT`).

**3.1.2** : `ConcertsAdminService.lister` renvoie la `situation` de chaque concert à confirmer (`jumeau` : même produit Eventim vivant sur une autre fiche de la salle ; `annoncee_ailleurs` : une autre billetterie l'a vue depuis moins de 7 jours ; `introuvable`), affichée par `AdminConcerts.vue` (`utils/situationConcert.js`).

**3.1.3** : la vue `concerts` (V105) expose la classification la plus fréquente parmi toutes les fiches de l'artiste reconnu (à égalité, l'ordre alphabétique ; sans artiste reconnu, celle de la fiche) : Découverte, Spectacles et leurs filtres affichent donc la même classification pour un artiste, `evenements.classification` restant celle de la source, lue telle quelle par le worker. Mesuré sur la copie de prod du dev : 19 ms pour la liste de Découverte (5 000 lignes), 57 ms pour la requête des filtres, `Memoize` sur l'artiste dans le plan.

`GlobalExceptionHandler.gererClientDeconnecte` ignore (niveau debug) `ClientAbortException` et `AsyncRequestNotUsableException`, l'exception de Spring qui enveloppe l'erreur d'entrée-sortie d'une réponse asynchrone abandonnée par le client : elle était journalisée en `ERROR` et déclenchait l'alerte d'administration.

`ClientController` journalise en `warn` (donc sans alerte d'administration, le digest ne reprend que les `error`) une erreur JavaScript marquée `masquee` par le front : « Script error. » sans adresse, ligne, colonne ni pile, que le navigateur masque pour un script d'une autre origine ou une extension, qui ne vient pas du code de l'application (même origine, détails fournis ; la CSP interdit tout script tiers) et ne peut être localisée. Les entrées d'erreur portent désormais le contexte envoyé par `utils/erreursClient.js` (`page`, `modeAffichage`, `enLigne`, `visibilite`) : l'`url` d'une erreur JavaScript est celle du script fautif, jamais celle de la page.

**Invitations par les utilisateurs (3.1.4, package `invitation`)** : `InvitationUtilisateurService` (aucun compte avant l'activation : table `invitations_utilisateurs`, compte créé par `activer` avec `users.parrain_id`, appelé en premier par `AuthService.activerCompteInvite` / `estTokenInvite` avant le lien `invite:` de l'admin) plafonne les invitations en attente (2 par défaut, `users.plafond_invitations` propre à un compte, 0 coupe l'invitation) et compte la cadence en base (`envois_invitations`, 5 par heure et par utilisateur, 30 par jour au total ; l'annulation ne remet rien à zéro). Deux demandes simultanées sont sérialisées par `SELECT … FOR UPDATE` sur la ligne du parrain (transaction ordinaire, jamais `REQUIRES_NEW` + `SERIALIZABLE`) ; `noRollbackFor = ErreurMetier` laisse la trace d'un dépassement dans `logs_admin` (identifiant du parrain, jamais d'adresse). Une adresse déjà inscrite ou déjà invitée reçoit la réponse d'un envoi réussi, sans email. `ReglagesInvitations` centralise plafond par défaut et cadence (`app_config` : `INVITATIONS_PLAFOND_DEFAUT`, `INVITATIONS_ENVOIS_PAR_HEURE`, `INVITATIONS_ENVOIS_PAR_JOUR`) ; `InvitationAdminService` règle plafond par défaut et plafond d'un compte (0 à 50) et trace chaque modification (`/api/admin/invitations/*`, `/api/admin/utilisateurs/{id}/plafond-invitations`). `UtilisateurAdmin` expose `parrain` et `plafondInvitations`.

`email.JetonInterne` (3.1.4) : contrôle unique du jeton `Authorization: Bearer <secret>` des endpoints internes (secret absent refuse tout, comparaison à temps constant, 403 identique) ; `BackupAlerteController` et `IntegriteAlerteController` l'utilisent, et `EndpointsInternesProtegesTest` échoue si un contrôleur qui mappe `/api/interne/…` ne l'appelle pas.

`core.RegleQuotaResend` (3.1.4) : la règle du quota Resend (clé `RESEND_QUOTA_JSON`, limites 100 par jour et 3 000 par mois, bascule jour/mois qui réarme l'alerte, réservation d'un envoi) n'est écrite qu'une fois ; `GestionQuotaResend` (web, `JdbcTemplate`, best-effort) et `GestionQuotaResendWorker` (worker, `NamedParameterJdbcTemplate`, transaction `SERIALIZABLE`, trois tentatives, journalisation du blocage) ne gardent que leurs écarts d'accès aux données, d'isolation et de trace.

**Profil et tri (3.1.4)** : `GET /api/user/profile` lit `users.two_factor_enabled` en base (`UtilisateurRepository.deuxFacteursActif`) et non plus le principal de la session, périmé après une activation ou une désactivation du TOTP jusqu'à la reconnexion. `FiltreConcertsBuilder.clauseTri` rend un ordre total (artiste puis heure puis identifiant, ou `first_seen` puis date puis identifiant) : sans lui, deux séances d'un même artiste le même jour se répétaient ou se perdaient à la frontière de deux pages de Découverte et de Mes spectacles. `DELETE /api/admin/invitations/envois` et `DELETE /api/admin/rate-limits/connexion` (profil `dev` seulement, appelés par le `global-setup` E2E) vident le journal de cadence des invitations et les limiteurs de connexion et de création de compte (`LimitesConnexionDevController`, `RateLimitingLoginFilter.reinitialiserLimites`) : des runs rapprochés n'épuisent plus le quota de 30 créations de compte par heure et par IP.

**Journal des accès non authentifiés (3.2.0)** : `ReponsesAccesApi.echecAuthentification` écrit son `warn` « Accès API non authentifié : <chemin> » par `LogAdminService.logAdminSansRepetition` : un même chemin n'est journalisé qu'une fois par 24 h (la même règle que le worker), les sondages répétés ne noient plus `logs_admin` ; l'IP et le User-Agent ne sont conservés que pour la première occurrence du jour.
